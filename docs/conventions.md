# 项目约定 {#conventions}

> 这些约定是多年讨论的结论，新增代码一律遵守。旧文档已归档至 `doc/archive/`。

## 命名

| 约定 | 示例 |
|---|---|
| **类名带 `_t`** | `object_t`、`property_t`、`widget_t`、`color_t` |
| **文件名与类同名** | `object_t.h` / `src/object_t.cpp` |
| **静态实例（命名常量、单例、默认对象）通过静态方法返回**，命名为 `xxx_<类名去掉 _t>` | `color_t::red_color()`、`color_t::white_color()`、`font_t::default_font()`、`widget_t::focus_widget()` |
| 命名空间小写下划线 | `hwshqtb::metaobject`、`hwshqtb::gui`、`hwshqtb::ui` |
| 内部实现放 `detail::`，**不导出** | `detail::core`、`detail::binding_scheduler` |

**静态实例规则的原因**：C++ 禁止静态成员函数与同名的非静态成员函数共存（如 `color_t::red()` 既是通道访问器、又是命名色工厂）。统一用 `xxx_<类名>` 后缀后，**通道访问器保留自然名字（`red()`），工厂永远带类名后缀（`red_color()`）**，不会再撞名，且一眼能看出返回的是该类的一个实例。

## 控件状态与事件

建模是成对的：

| 概念 | 是什么 |
|---|---|
| **USER 事件** | **改变状态的那个事件**（每类至多一个） |
| **状态** | 它的 **`notifier` 指向的那个可写属性** |

两者不需要额外标记或约定——**链接就写在元数据里**（属性的 `notifier`）。下表是推论：

| 规则 | 说明 |
|---|---|
| **顺着链接找状态** | 先取本类的 USER 事件，再找 notifier 解析到它的可写属性。通用状态快照就按这条链接来，不需要"哪些属性算状态"的白名单 |
| **命令型事件没有状态** | 例：`push_button_t::clicked`。它仍是 USER 事件（是 `control()` 的结果通道），但没有属性链接它 → 零状态 → 快照不建条目 |
| **什么不是状态** | 配置（`minimum` / `maximum`）、每趟由调用方给的（滚动偏移）、瞬态交互（焦点、指针捕获、光标位置）、布局给的（几何、可见、使能） |

**为什么**：即时宿主的状态仓库必须能为**任意控件**做快照而不写 per-control 代码。有了这条链接，规则就是"顺着 USER 事件找到状态"，而不是靠"声明类在谁之上""可写""非 USER"这类启发式去猜——猜出来的东西会在建模变化时静默失配。

**词汇**：`activated` 属于 item view（选中并激活），按钮用 `clicked`。不要混用。

## 头文件与实现

| 规则 | 说明 |
|---|---|
| **成员函数实现放 `.cpp`** | `inline` 只是 ODR/链接标记，不是内联保证；头文件里的实现会在每个消费者 TU 里各生成一份 |
| **例外：`constexpr` / `consteval` / 模板** | 常量求值与模板实例化要求每个 TU 可见定义——这类必须留头文件 |
| **`= default` / `= delete`** | 留在声明处 |
| 头文件只放声明 + Doxygen | 实现文件只写实现，注释从简 |

## 成员声明顺序

同一个类里的成员按固定顺序排列，读代码时不必跳着找。**只约束顺序，不约束内容。**

| 位置 | 内容 |
|---|---|
| 类首 | `META_*` / `OBJECT` 宏 |
| `public:` | ① 构造 / 析构 / 拷贝移动（`= delete` 紧随其后）<br>② 类型与枚举（类内定义时）<br>③ 属性访问器——**成对，getter 在前、setter 在后**<br>④ 普通公开操作（常用在前）<br>⑤ 框架入口的覆写（`is_item` / `child_added` / `paint` / `hit` / `interact` / `event`）<br>⑥ 别的对象的**上报/落点入口**（非虚、成组、注释里写明调用方，例如「平台实现调用」「宿主落点」）<br>⑦ `SIGNAL` 声明（段末） |
| `protected:` | ⑧ 事件处理器覆写，按固定顺序：`paint` → `hover` → `press` → `focus_change` → `geometry_change` → `size_constraint_change` → `content_change` → `data_change` → `rows_change` → `visible_change` → `enabled_change`<br>⑨ 供子类使用的钩子与工具 |
| `private:` | ⑩ 私有辅助函数（按首次调用顺序）<br>⑪ 数据成员（按主题分组，组间空行） |

三条理由：

- **覆写集中放置**：一眼看出这个类覆写了哪些框架入口，而不是按"它属于哪个接口"散落在公开 API 之间；
- **setter 永远跟在 getter 后面**：成对出现，不会出现"先设后取"的错觉；
- **同类相邻**：`update()` 家族、`set_*_sink` 家族、事件处理器序列各自连续。

⑥ 的理由：一个类被**另一个对象**回调（平台半边回调窗口、窗口回调宿主）时，那些入口既不是属性也不是
给应用调用的普通操作，混在④里会让人以为应用也该调。单列一组并标明调用方后，"谁能调这一组"读注释即可。

## 导出

| 规则 | 说明 |
|---|---|
| **`HWSHQTB_*_EXPORT` 标在类上，不标在定义上** | |
| **接口模板不导出** | 导出会强制 `dllimport`，破坏常量表达式 |
| `friend` 运算符单独导出 | 类级标记不覆盖 friend |
| 被消费者调用的自由函数需单独导出 | 库内私有函数**不应**出现在导出表 |

## 头文件交付

库以头文件交付，没有 C++ 模块。**每个公共头必须自足**：单独 `#include` 它就能编译（`reflection.hpp` 曾因缺 `annotation.h` 破过这条）。消费者只 include 自己用到的头，不用伞头；往测试里加一个库名字时，必须同时加它的头。

## 日志宏

`HWSHQTB_LOG` / `HWSHQTB_LOG_RAW` / `HWSHQTB_DEBUG|INFO|WARNING|CRITICAL|FATAL`，以及各自的 `_DEFAULT` 形式（走 `default_category()`），定义在 `include/hwshqtb/metaobject/log.h`。

| 规则 | 说明 |
|---|---|
| **先查后格式化** | 宏先把分类绑到局部引用并 `is_enabled(level)`，通过后才构造消息——关闭级别上消息参数**不会被求值**，`std::format` 的开销不付 |
| **带源位置** | 宏自动填入 `__FILE__` / `__LINE__` / `__func__`，`log()` 再把分类名写进 `log_context_t::category`；直接调 `log()` 只留给"要自己带 context"的场合 |
| **消息已算好就用 RAW** | 拼好的字符串/表达式用 `HWSHQTB_LOG_RAW`；`std::format` 风格用 `HWSHQTB_LOG` 或级别宏 |

## 测试与验证

| 规则 | 说明 |
|---|---|
| 每个里程碑带一个覆盖验收标准的测试 | `tests/implementation-test/m*` |
| **重构不得减少被改动测试的断言数** | 迁移是等价改写；被触碰的测试数字下降即失败。**其它测试不做计数核对** |
| 无窗口/无显示器可运行 | GUI 测试一律离屏渲染 |
| **构建验证只跑 `Release-shared`** | 只配 `build\GCC 16.2.0 x86_64-w64-mingw32 (ucrt64)-Release（METAOBJECT_SHARED=ON，即共享版 Release）`。不再验证四目录。<br>**例外**：怀疑问题只出现在静态链接或 Debug 语义（ODR、`constexpr` 求值、断言宏）时，单独指定再跑并说明理由 |
| **不要过度测试：只验证被改动的那一部分** | 改什么就编译什么、跑什么：<br>· 改核心/跨层 → 跑 `ctest`（全部 80 个）<br>· 改某个测试或某个类 → **只跑该测试**<br>· 改渲染/事件循环/window → 才跑截图与 `--self-test`<br>· **不要求**每轮都跑全量 ctest、截图哈希、断言计数。截图与计数只在**确实被改动**时核对 |

**为什么**：全量验证每轮要跑几十秒到几分钟，而这些时间换来的信息在"只动了一个枚举值"时几乎为零。**把验证预算花在真正被改动的路径上**——该跑的一条不少，不该跑的一条不加。

## 工作方式

| 规则 | 说明 |
|---|---|
| **起始代码是可编译、可运行的** | 上一次验证已经通过。**不要**重新验证基线，不要"先跑一遍看看现在行不行"，不要因为改了一个文件就重跑全部测试 |
| **只按要求修改** | 任务清单之外的东西一行都不动——不改名、不重排、不"顺手"修邻近的注释或格式 |
| **只按要求验证** | 验证范围 = 改动的影响面。改 A 就构建 + 跑覆盖 A 的测试；A 之外的测试不跑、不数、不核 |
| **不写防御性条款** | 不要在任务里加"先探针确认""若编译失败就停下报告""如有必要再确认一次"——除非确有**未知**（例如新的编译器行为、未验证过的平台特性）。已知能编译的代码不需要先证明它能编译 |
| **直接增量构建，不清理、不重配** | 用 `cmake --build "build\GCC 16.2.0 x86_64-w64-mingw32 (ucrt64)-Release"` 即可。**不要**先删构建目录、不要重新 `cmake -S . -B`、不要"构建两次以防陈旧"。依赖由 Ninja 负责——缓存是可信的 |
| **结束输出就是汇报** | 子代理的收尾消息即报告，**不要再单独索要汇报**。任务里也不必单列"报告清单"——做了什么、改了什么、结果如何，收尾消息自然会说 |
| **有疑虑就停下汇报，不测试、不修改** | 一旦发现"这样改可能有问题"——**立即在收尾消息里说明，不要自行测试验证，也不要顺手改掉**。判断权在决策者，执行者只负责如实上报 |

**为什么**：这些防御性步骤每一条都在花时间确认**已经成立**的事实。代码是可编译的，构建通过不是信息；测试通过不是信息——**只有"改动是否正确"才是信息**。

## 文档

- 公共实体一律 English Doxygen；
- 设计文档记录**决策与理由**，不只是 API 列表；
- 设计变更时同步文档——规格说谎比代码有 bug 更危险。
